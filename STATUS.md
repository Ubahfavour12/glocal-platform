## How we work: `dev` builds, `master` goes live

Two branches, and the difference is what Vercel does with each.

| branch | what it is | what Vercel does |
|---|---|---|
| `dev` | where all work lands first | builds a **preview URL** you can open and check |
| `master` | production | builds the **live site** |

So nothing reaches the live site by accident. Work goes to `dev`, you get a
preview link to look at, and only a deliberate merge promotes it.

**The daily loop:**

```bash
git checkout dev          # work here, always
# ... changes happen, commits happen, the hook pushes them ...
```

**When you are happy with the preview and want it live:**

```bash
git checkout master
git merge --ff-only dev   # refuses if master has drifted, which is the point
git push origin master    # Vercel builds production
git checkout dev          # go straight back to dev
```

`--ff-only` is deliberate. It refuses to merge if `master` has commits `dev`
does not, which means someone committed straight to production. Better to be
stopped and told than to have two histories quietly diverge.

**On a second machine, before starting anything:**

```bash
git checkout dev && git pull
```

The post-commit hook guarantees work goes **up**. Nothing guarantees it comes
**down**. That direction is still yours, and skipping it is how you end up with
two copies that disagree.

## Keeping this file honest

The table at the top updates **on every commit**, without anyone remembering to
do it. A `pre-commit` hook runs `npm run status` and stages the result, so the
file always describes the exact commit it travels in. You can run it by hand too
(`npm run status`), but you should never need to.

A status file written by hand goes stale, and a stale one is worse than none:
confidently wrong, and believed. The generated part cannot drift; everything
below it is judgement and stays hand-written.

## Two safeties in the hooks

- **`dev` pushes itself** the moment you commit, so work is backed up
  immediately and gets a Vercel preview URL.
- **`master` never pushes itself.** Vercel builds production from `master`, so
  pushing it is publishing to customers. That stays a deliberate command you
  type, never something a hook does for you.

## What was built most recently

Newest first. `git log` carries the full reasoning for each; commit messages
here are written to be read later, not to be terse.

- **Onboarding money screen, from the phone review** — the number was called a
  "hold" on three screens when it is actually the minimum balance the wallet
  needs before ads can start. Nothing is taken, and now it says so. The word
  "hold" is reserved for the real daily budget hold. The screen also showed two
  of its four cards above the fold while the button already said "I understand";
  it now shows all four.
- **Business start year** — asked once at onboarding, optional, gates nothing.
  A retention signal: a shop in its first year and a shop of fifteen years churn
  for different reasons, and one number cannot tell them apart. Needs migration
  `0024`.
- **"WhatsApp conversations" vs "Sales"** — the two goals read as near-synonyms.
  Now each says what it actually counts: chats opened, versus money, which needs
  telling which ad earned it.
- **Withdrawals, refunded to the original payment** — a customer asks for their
  unspent balance back and it returns to the card or account that paid it. No
  bank details are asked for, stored, or transmitted, so there is nothing to
  mistype and nothing an attacker can redirect: someone who takes over an
  account can only send money back to a card that is not theirs. Needs
  migration `0021`.
- **Migrations `0021`–`0024` applied** (8 Sep) — withdrawals, ad-budget holds
  and the business start year are live in the database, verified by counting
  the tables, types, enum value, column and functions rather than by trusting
  the run.
- **Refunds actually get sent** — a withdrawal reserved the money and worked
  out which payments to give back, and then nothing sent them. A daily job now
  does, one at a time, claiming each refund before calling the rail so a
  crashed or overlapping run cannot pay anyone twice. Refunds convert back at
  the rate the customer originally paid, not today's.
- **Both money rails, with failover** — if the first rail cannot produce a
  checkout link, the other is tried and the customer gets a working link rather
  than an error. Safe precisely because creating a link moves no money; it is
  deliberately not extended to verification or settlement, where a retry would
  be a second charge.
- **Charging in the customer's own currency** — checkout was quoting every
  customer in naira regardless of where they signed up. It now uses the
  currency stored at signup where the rails can settle it, and USD where they
  cannot, with the conversion behind the screen. USD stays the ledger anchor.
- **Onboarding drafts stop leaking between accounts** — the half-finished run
  lives in browser storage, so abandoning a signup and returning as a different
  email handed the next person the previous one's business name, phone and
  budget. Drafts now carry who they belong to and are discarded when that is
  someone else.
- **Ad budget leaves the wallet on launch** — the day's budget, plus its
  markup, is held out of spendable balance the moment a plan goes live rather
  than hours later when the network reports delivery. Holds are released when
  the day is done, so nothing is ever held for ads nobody ran. Needs migrations
  `0022`–`0023`.
- **Pipeline page fixed** — it had been throwing a 500 for any account that
  actually had concepts since 15 August. A Server Component was passing a
  function across the client boundary; the empty state returned first, so a new
  account looked fine and it only broke once the agent had done its job.
- **Sign-in links say why they failed** — a failed link redirected to an
  ordinary empty email box, which reads as the product ignoring you. It now
  distinguishes a link opened on the wrong device from one that has expired.
- **Video choice + cost recording** — Pipeline offers image or video per
  concept, priced (`video · 4x`) and disabled with a reason when the day's
  allowance cannot cover it. Every creative records which engine made it and
  what that engine charges.
- **Engine router** — both engines live from the start. Free tier is always
  fal; video prefers Higgsfield; images prefer fal; a missing key never stops a
  render. Rules are labelled as decisions or as facts, never confused.
- **The logo**, traced from the final artwork into the product.
- **Onboarding**, rebuilt as seven phone screens.

## The road to 100%

"100%" means: a shop owner who has never met you can sign up, pay, and have ads
running and improving without anyone touching it.

### Where we actually are

The **product is close**. The **business plumbing is not connected**. Almost
nothing left is engineering.

| area | state |
|---|---|
| Onboarding, dashboards, duel, verdicts, wallet, ledger, approvals | built and tested |
| Creative pipeline: concepts, rendering, engine routing, compliance | built and tested |
| Meta ad lane: campaigns, ad sets, creatives, insights, age/geo rules | built, **never run live** |
| Money: subscriptions, markup, statements, receipts, Flutterwave | built, **no live keys** |
| Anything requiring an outside account | blocked |

The honest summary: **the code is roughly 85% of v1 and the launch is roughly
30%**, because the remaining 15% of code is small and the remaining external
gates are large and slow.

### The critical path, in order

Everything else can happen in any order. This chain cannot.

1. **Buy `useglocal.ai`** — cheapest item, sits upstream of the largest one
2. **Business email on that domain** — Meta review treats a gmail address as weak
3. **Meta Business Verification** — days, sometimes weeks
4. **Meta App Review** — the master switch. Until it passes, **no ad can run
   for any customer**, and every screen in the product that matters is theatre
5. **Payment method on the Meta child ad account** — the last step before a
   real ad spends a real naira

Nothing about ads works until step 4 clears, and step 4 cannot start properly
until step 1 exists. That is the whole shape of the delay.

### Code still to write

Small next to the gates above.

1. **Apply migration `0025`** to Supabase — a security fix, not a feature.
   `record_sale` could be called without signing in, and its ownership check
   used `<>` against `auth.uid()`, which is NULL for an anonymous caller, so the
   guard evaluated to NULL and never fired. Anyone knowing a business id could
   forge the sales the duel judges ads on.
   The code fails soft without them: the wallet page still renders and the
   withdraw button stays hidden, so nothing is broken in the meantime
2. **Founder admin console** — every customer, wallet, verdict and error in one
   view. Wanted **before** the dogfood, not after. Should also be where a
   requested withdrawal is marked paid, which is a manual step until a payout
   API exists
3. **Sentry + PostHog** — needs two free accounts creating
4. **Directions taps** as a counted footfall signal
5. **Retention cohorts by business age** — the start year is captured but
   nothing reads it yet. Worth doing once there are enough customers for the
   answer to mean anything, not before
6. **The rest of the congestion pass** — the money screen was reviewed and
   fixed on a phone. The other six onboarding steps have not had the same
   look, and neither have the dashboard screens

**Paystack** has moved off this list — the rail is built and tested, and now
waits on a key like everything else. `PAYMENTS_PROVIDER` chooses which rail new
checkouts open on; both webhooks stay live whichever is chosen, so a charge
already in flight still settles after a switch.
